# Security review - Wbcom Essential 4.7.0

Scope: `v4.6.3..4.7.0`, the plugin's own code as shipped in the zip (`vendor/`, `.phpstan-stubs/`, `scripts/` excluded; the stubs are analysis-only Elementor sources and never ship).

## Result

No CRITICAL or HIGH findings. One MEDIUM and two LOW, all fixed in this release.

| Severity | Finding | Status |
|---|---|---|
| MEDIUM | The 4.7.0 checkout migration could run on a logged-out request (`admin_init` also fires for `admin-ajax.php` / `admin-post.php`), and `wp_update_post()` then passed the content through kses, stripping any script, iframe or custom HTML the owner kept on the checkout page. Same on multisite for admins without `unfiltered_html`. | Fixed: `includes/upgrades.php` removes the kses filters around its own rewrite and restores them after. The runner moved to `wp_loaded` so the first request after an update migrates the site without anyone visiting wp-admin. Verified on a pristine install: a 4.6.3 checkout page with an inline `<script>` kept it after a logged-out upgrade. |
| LOW | `GET /wp-json/wbcom/v1/products` (and the server-rendered Product Catalog) listed password-protected downloads with a 20-word excerpt of their content. The REST part predates 4.7.0. | Fixed: `'has_password' => false` in `includes/edd-product-catalog-rest.php`. |
| LOW | The catalog's initial JSON payload in a `<script type="application/json">` could be pushed into the HTML parser's double-escaped state by a product title containing `<!--<script`, swallowing the rest of the page. Not XSS (`wp_json_encode()` escapes `/`). | Fixed: `JSON_HEX_TAG \| JSON_HEX_AMP` in `product-catalog/render.php`. |

## Mechanical sweep (G1)

Same counts as v4.6.3 on shipped code; files without a direct-access guard went from 3 to 1.

## Scanner-visible but safe

- `wp_ajax_nopriv_wbcom_ajax_login` (`plugins/elementor/wbcom-essential-elementor.php`): the Login Form widget's endpoint, for logged-out visitors by definition; nonce is CSRF protection and `wp_signon()` runs core's `authenticate` chain. The pre-existing LOW open redirect (`redirect_to` accepted an external URL) is fixed in 4.7.0 with `wp_validate_redirect()`; verified in a browser that an external target lands on the home page and a same-site target still works.
- "Nonce-only" handlers `wbcom_essential_dismiss_elementor_notice` and the template manager AJAX actions: each also checks `current_user_can()` (`manage_options` / `edit_posts`).
- Software Licensing views opened from the account dashboard (`?action=manage_licenses&license_id=&payment_id=`): the ids only choose which SL template loads; EDD SL's templates check the licence/payment belongs to the current user (or `manage_licenses`).
- Subscription Upgrade Plan / Extend / Renew links: built server-side from the customer's own rows, no request input.
- Update Payment Method: dashboard passes `absint( subscription_id )` to EDD Recurring's `subscriptions_view( 'update' )` after the customer guard; ownership and the `update-payment` nonce are enforced by EDD Recurring. Not re-verified here (Recurring not installed locally).
- `wbcom/v1/edd-account/{tab}`: `is_user_logged_in()` plus a tab enum; every tab renders only the current customer's data through kses.
- `wbcom/v1/products` and `product-categories`: public by design; published downloads only, enum/absint args, page size capped at 48.
- `wbcom_essential_edd_free_plugins_top` output: buffered and passed through `wbcom_essential_kses_form()` on both the REST and block paths.
- `includes/upgrades.php` SQL: a static `LIKE` with no user input.
- Preset licence activation retry (`admin-post.php?action=wbcom_essential_retry_preset_activation`): `manage_options` + `check_admin_referer`, remote URL is a constant, `wp_safe_redirect()`. The bundled key is the deliberately public free-distribution key. No usage-tracking option is written.

25 errors on 4.6.3, 0 on 4.7.0 (translator comments, documented render_block() escaping exceptions, the settings heredoc moved to a script file, header/readme Tested up to aligned).

## QA round (release held, 2026-10-08)

QA rejected the first 4.7.0 tag with three cards; all reproduced on the rejected zip and fixed:

| Severity | Finding | Fix |
|---|---|---|
| MEDIUM | `POST /wbcom/v1/edd-account/claim-free` let any logged-in customer claim a password-protected $0 download by id, creating a completed order and library access without the password. | `post_password_required()` added to `wbcom_essential_edd_claim_free_callback()`; a customer who entered the password (WordPress's wp-postpass cookie) can still claim. Verified: protected id returns 400, public free still 200, after entering the password 200. |
| LOW | The account dashboard's What's New, Free Plugins and Recommended (category fill and Pro counterpart) listed password-protected downloads with title, price and link. | `has_password => false` on the three customer-facing download queries; `wbcom_essential_edd_get_pro_counterpart()` skips protected products. The admin counterpart picker and the licence-name search keep protected products on purpose (admin-only / the customer's own licences). |
| n/a | Forums and Forums Activity widgets: PHP warning for topics with no replies (bbPress stores 0 as the last reply id). Pre-existing, not security. | Fall back to the topic id and guard the reply branch with `bbp_is_reply()`. |
